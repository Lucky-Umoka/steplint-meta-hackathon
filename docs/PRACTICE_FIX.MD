# 1. FIRST DIAGNOSIS


The root cause of why Practice mode is "lifeless" is an **architectural flaw in the frontend loop**. 

Here is exactly what is happening under the hood: Your frontend is waiting for a backend API response (`/api/perceive` or similar) to tell it whether a step passed or failed. Because sending a frame to the server and running SAM 3.1 takes 2–5 seconds, your UI just sits there doing nothing. It is **event-driven instead of continuous**. 

To fix this, we must implement the **Sensor Fusion** loop. The browser must run a continuous local loop at 30 frames per second, check the coordinates against the deterministic rules instantly, and fire the UI red lights and voice warnings *in the same millisecond*. 

We also need to ensure the **Teach** flow actually outputs strict `zones` (bounding boxes) so the local tracker knows exactly what to look for. If the Teach output is vague text, the verifier has nothing to check.

Here is the master prompt to give to Codex/Muse. It forces the AI to fix the architecture, not just patch a bug.

# 2. SECOND DIAGNOSIS

You asked for the root cause rather than symptoms, so I'm checking the layers you named. I'm looking at what Vercel ships (config, ignored files, signing keys) and at what the browser has to start for Practice to go live.

Still on the root cause: the probe shows setup failing on a smooth table. Now I'm testing whether a textured surface under the objects fixes it, because that would be an immediate demo fix.

**Root cause:** Practice is built to re-find your Teach scene pixel-for-pixel, and the real camera never reproduces it exactly. It isn't your browser, Vercel, or how the guide was generated.

**The mechanism**
1. **Setup, step 1:** at Practice start, `bootstrapLocal` aligns the live frame to the saved Teach frame. That step needs clear, static texture on the work surface (`automatic-alignment.ts`).
2. **Setup, step 2:** it then requires each object to match its Teach-time appearance at 0.90 or better. Fixed destinations must sit within about 1.5% of where they were.
3. **No fallback:** after 5 failures it gives up ("Automatic setup keeps failing"), and with no calibration there is no tracking at all. That is why you see no liveness.
4. **Mid-practice:** if the fixed reference moves, calibration is invalidated and verification stops.
5. **Why the tests miss it:** the tests use synthetic scenes where every pixel is random texture. The suite itself asserts that textureless scenes are rejected.

**Evidence from a probe I ran**
I built a webcam-like synthetic scene (320×240) and perturbed it. This is not your footage.

| Scene | Result |
|---|---|
| Smooth table | Passes only for a bit-identical frame. A different noise seed, a 1 px camera shift, ±10% brightness and normal sensor noise all fail. |
| Patterned table | Tolerates up to 8 px of camera shift, noise and ±10% brightness. Fails at +25% brightness and when the fixed tray is bumped 6 px. |

The second failure is what auto-exposure does when your hand enters the frame.

**Other layers**
- **Teach:** only partly involved. The Teach frames are the reference being matched against, and that coupling is the flaw.
- **Browser:** no CSP headers are set, and the worker and assets ship fine.
- **Vercel:** Practice runs locally in the browser, and signing keys come from env vars rather than per-process randomness. Check that `TEACH_ACCESS_TOKEN` matches in every environment you use, or signed lessons won't verify.

# 3. THIRD DIAGNOSIS

I think the reason you've been moving in circles is that we've been trying to fix Practice without first proving where the connection between Teach and Practice breaks.

We need to stop changing random parts of the application. We need to trace one real guide through the entire system and identify the first point where the expected behaviour stops.

My current suspicion is that this is not simply a Baseten problem. Baseten is involved in generating the procedure in Teach. Practice has a separate responsibility: receive a valid approved guide, observe the learner through the camera, interpret what is happening, and feed those observations into the verification engine.

If that chain is broken at any point, Practice can look completely dead even when some of its individual components work.

I don't think we should rewrite Practice. I also don't think we should start by changing the camera, the worker or the verifier independently.

The most likely underlying problem is the gap between synthetic/test observations and reliable real-world camera observations.

In other words, StepLint knows what to do when it receives valid tracking data. We haven't yet demonstrated that it consistently receives the right tracking data from your actual physical task.

That is why I cannot honestly name one specific failing line of code yet.
